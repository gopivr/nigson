# ADR-034: Customer product return requests after delivery

Status: User-authorized implementation, 22 November 2026.

Commerce owns one-product return requests with exact quantities and frozen commercial returns-policy revision. Customer eligibility requires owned delivered order/fulfillment, authoritative delivered shipment quantities and original stock-dispatch evidence. Customer selects a product, quantity and reason. Requests reserve the returnable quantity under the order lock. REQUESTED -> APPROVED/REJECTED; APPROVED -> RECEIVED after Operations records physical receipt and inspection. Rejection releases the request quantity; receipt does not undo delivery. Prior legacy physical returns and accepted requests cap cumulative quantity. One product per request supports partial and multiple-product returns without ambiguous per-line decisions.

No return window, return fee, shipping address or carrier eligibility is invented from a policy revision. Operations reviews against that frozen policy and supplies customer-facing return instructions. PandaGo reverse pickup is not configured by this increment. Receipt has a required external reference and an explicit restock decision. Restock uses original dispatch balances and the existing idempotent StockLedger PHYSICAL_RETURN path; damaged/nonrestock receipts do not increase saleable on_hand. Receipt and request state/audit commit together. Provider HTTP is absent from return transactions.

After receipt, current Finance/recent MFA may explicitly request a chosen amount on the original verified Paystack settlement, within existing successful/active refund caps. Tax/delivery allocation is a Finance policy decision, not an automatic calculation. Return records link one refund request; the existing Finance/two-person approval, stable provider reference, worker, webhooks and UNKNOWN reconciliation remain authoritative. No refund is sent when merely requesting/approving/receiving a return. COD without verified collected Paystack settlement remains returnable physically but needs Finance payment resolution outside automated Paystack refunds. Delivery history remains DELIVERED even after a full return/refund (order status may follow the existing financial REFUNDED convention).

New API-237..243 are Commerce BFF/session routes with current owner or Operations/Finance authority, CSRF, exact If-Match and durable idempotency. Owner-local additive Commerce038 return_request table has no cross-owner references. Receipt and refund identifiers are immutable once set. Return, quantity and payment states remain separate. Customer and staff lists are bounded and reject overflow rather than silently hiding return reservations. All Commerce artifacts must honor the physical-return cap before rollout; populated rollback refuses. No new business provider, dependency or service.
