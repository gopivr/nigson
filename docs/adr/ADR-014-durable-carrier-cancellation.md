# ADR-014: Durable carrier cancellation and dispatch exclusion

Status: Accepted technical design; implementation/acceptance IN_PROGRESS.

Required launch cancellation needs an application command and a durable source dispatch exclusion; the existing HTTP adapter alone is insufficient. Add commerce.carrier_cancellation and integration.carrier_cancellation as owner-local additive BP1 tables, with separate application/migration roles and no cross-owner SQL/FK/shared entities. Existing applied DDL/checksums remain untouched. Commerce locks order then shipment before accepting an unshipped FEDEX/BOOKED cancellation intent. Its active-request partial unique index and the dispatch guard serialize cancellation against physical handover. Cancellation never refunds money or returns stock automatically.

Add API-197 POST /api/v1/staff/shipments/{id}/carrier-cancellation (reason, current OPERATIONS/recent MFA, CSRF/If-Match/key) and API-200 GET on that path for current status. A durable source relay sends original approved facts over API-198 POST /internal/v1/carrier/cancellations with exact commerce carrier.cancel workload scope and no browser/actor token. The staff decision is recorded and audited before asynchronous execution, like the existing paid-order booking event. Relay failures preserve the original cancellation UUID/request and source dispatch exclusion. Source current-read authority still applies; later staff revocation cannot erase previously accepted business evidence.

Integration validates the original booking/mode/account/master/piece identities. It persists one cancellation intent per source UUID and fences leases/versions before any provider cancel. A separate SUBMITTING checkpoint commits before HTTP. A restored/expired/submitted/unknown intent never regains cancellation-write permission; externally configured generation/source-event cutoff apply to fresh cancellation writes too. Accepted unknowns reconcile by saved physical-piece tracking, never another cancel or shipment creation. Rejections and cancellation proof remain distinct; missing/ambiguous evidence stays UNKNOWN.

API-199 POST /internal/v1/carrier/cancellation-results uses exact integration logistics.write workload trust, original cancellation/request identity and a durable callback UUID. Source atomically records ACK/audit/status/history/outbox with its cancellation intent under order/shipment locks. Confirmed cancellation may cancel only an unshipped matching shipment; rejected cancellation releases the dispatch exclusion; UNKNOWN preserves it. Callback/reply loss replays the original body/UUID. Source physical/terminal guards remain authoritative. A new explicitly authorized staff intent after a known rejection is separate from automatic retry of uncertainty.

Migration analysis: new tables/indexes/owner-local FKs only; empty rollback may remove this increment, populated rollback refuses before any drop. Upgrade must retain all prior checksums and representative booking/shipment evidence. No change to existing public shipment DTOs, money, inventory ledger or booking event. New endpoints/scopes/default-off flags require reviewed contract/native/identity qualification before acceptance; real FedEx route/account and private deployment qualification remain NOT_RUN.

Primary protocol: https://developer.fedex.com/api/en-us/catalog/ship/v1/docs.html and official Shipment-Resource.json/API1.0.0 SHA256 ebc4248f99bd04cd5d7a815cb2b6c089ab72291afd6bf5980e329979102acc53. The reviewed request uses the saved master tracking/account and DELETE_ALL_PACKAGES; it does not schedule a return, refund or assume route eligibility.

API-198 replies include the persisted original receipt when one exists. The authenticated source relay can apply that receipt through the same logical receipt-dedup namespace as API-199; audit distinguishes inbound workload from source relay ingestion. Replaying a terminal cancellation request after source restore therefore recovers its original result without another carrier cancel. API-200 exposes current source cancellation/shipment versions, while public POST replay resolves its original durable intent.

Rollout requires all commerce instances to implement the new dispatch exclusion before enabling new cancellation intents. An older unguarded commerce artifact must not run while active cancellation intents exist; disable new requests and resolve/reconcile existing work or roll forward. Populated rollback refuses, and genuine ECS rollback/restore qualification remains a BP1 gate.
