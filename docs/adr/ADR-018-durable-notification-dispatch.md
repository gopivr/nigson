# ADR-018: Durable notification dispatch identity

Status: Accepted technical design; MSG-001 intake/execution IN_PROGRESS.

The existing notification_job identifies a template revision but cannot freeze locale/template facts, account/service identity or a provider SUBMITTING checkpoint. Add integration.notification_dispatch, paired one-to-one with the existing owned job. Freeze the validated static template (no rendered phone/code), template hash, original account/service/mode identity, externally supplied creation generation and original source-event time/correlation in the same transaction as job/audit/inbox. Existing applied migrations/checksums remain untouched; additive BP1 migration uses owner-local FKs only. Rollback refuses populated intent; no automatic legacy backfill.

EVT028 produces the deterministic job UUID already specified by ADR-017. Business key includes channel/destination/proof; replay preserves original template/account/mode/state/lease/source metadata. A job without its paired intent is UNKNOWN/integrity failure, never permission to manufacture another provider call. A semantic replay does not adopt current configuration. Select an explicitly configured active CONTACT_VERIFICATION template revision/locale/channel; classification must be TRANSACTIONAL, schema/code fields closed, no executable template language. No guessed sender/template approval or real provider qualification is inferred.

Fresh provider writes require current identity/generation/source cutoff and unexpired authoritative source context. Persist SUBMITTING before unlocked HTTP. Expired/submitted/UNKNOWN checkpoints never regain fresh send permission; recover only through matched provider receipts/status. Request identity must use a keyed digest rather than a brute-forceable bare proof/phone hash; rendered code/phone is not durable dispatch/audit/telemetry data. Future sender/receipt implementation must qualify these stages before activation; durable intake alone acknowledges PENDING work, never SENT or DELIVERED.

Account fingerprint is canonical SHA256(provider TWILIO, actual transport MOCK/TEST/LIVE, account SID, messaging-service SID); credentials are excluded so same-account credential renewal preserves identity. Original account/service metadata is retained to validate historical results after configuration changes; no rotation overwrites original intent. Callback job/account/SID matching cannot authorize another send. EMAIL/newsletter and inbound WhatsApp/SALES workflows retain their own owner contracts. Real account/sender/template/retention, private deployment and restore qualification remain NOT_RUN. No critical approval blocks offline engineering.

Intake implementation accepted offline at 99e3c13137bbcb66238106ca0790670bb16e68e2 (native44/no skips,78 contracts, previous BP1/rollback and provider regressions). Sender/receipt execution remains IN_PROGRESS.
