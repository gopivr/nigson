# ADR-033: Customer order cancellation with PandaGo and Paystack

Status: User-authorized implementation, 22 November 2026; supersedes API-040 unpaid-only restriction.

Commerce persists one order cancellation intent before external work, exposing additive cancellation status in OrderDTO. API-040 retains its reason/If-Match/idempotency/ownership/CSRF contract and returns 202 while pending, 200 after completion. Cancellation excludes processing, booking and dispatch under the order lock. Delivered/physically dispatched orders use returns and cannot self-cancel. UNKNOWN payment/booking/carrier outcomes retain exclusion and never imply success.

Integration implements API-198 using existing workload trust and owner-local carrier cancellation checkpoints. Cancellation and booking preparation serialize on the booking row. Unprepared bookings can be suppressed locally; prepared bookings without a provider ID remain UNKNOWN. Provider DELETE occurs once after a durable SUBMITTING checkpoint, subject to external generation/cutoff/account/mode/approval checks. Recovery is read-only. 204 proves cancellation; legacy 203 requires GET proof. Authoritative refusal differs from uncertainty. The original durable receipt is returned through the existing Commerce relay; no cross-owner SQL. API-199 remains available for authenticated result delivery.

Commerce cancels all unshipped deliveries before inventory release. Reserved stock is released and allocated stock reversed through StockLedger without increasing on_hand. A monetary refund never proves a physical return. Remaining captured payment becomes a REQUESTED refund, using existing Finance approval (including two-person policy), Paystack submission and reconciliation. Requested cancellation authorizes requesting the remaining captured amount, including the frozen delivery amount; no invented provider charges are deducted. Existing active refunds are accounted for. COD with no collection creates no refund. Cancelled fulfillment cannot reopen after refund failure or late payment. Late verified payment remains financial truth and creates refund work without recovering cancelled stock.

Migration: additive Commerce cancellation table plus widened owner-local carrier references; prior changesets remain immutable. Existing carrier intent reference remains stable even when booking acknowledgement supplies a real provider ID later. Populated rollback refuses; expand deployment requires every Commerce artifact to honor exclusions before accepting requests. Default-off carrier execution requires explicit activation; unavailable providers retain pending customer requests. Real provider/browser qualification is separate from isolated tests.
