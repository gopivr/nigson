# ADR-011: Private carrier label production and source ACK recovery

Status: Accepted technical implementation decision; cloud/print/provider activation remains NOT_RUN.

Integration parses only the embedded LABEL/PDF documents returned by its configured FedEx adapter, validates complete unique package/tracking coverage, rejects encrypted/active/external-file PDF structures, and merges pages through pinned Apache PDFBox3.0.8. Input/output bytes, package/page counts, object traversal and page geometry are bounded. Labels are ordered by tracking number, document metadata is fixed and document identifiers derive from the original labels, making retry bytes deterministic. No provider document URL is fetched. This is a trusted carrier PDF profile, not a general user-upload malware scanner or evidence of barcode/print qualification.

The existing API-120 storage handoff authorizes integration to put only immutable generated labels under `<env>/commerce/shipping_label/<shipment>/1/pdf` in the explicitly configured commerce private bucket. Integration retains its own PostgreSQL role/schema; it never writes commerce tables or creates shared entities. An independent real S3 client uses TLS/SigV4, dummy credentials only for allowlisted local/test HTTPS targets and ECS task credentials/KMS outside local/test. PutObject always uses If-None-Match:* with SHA256 and trusted booking UUID metadata. A lost response is resolved by versioned encrypted-object HEAD with exact owner/size/MIME/checksum proof; a conflicting existing object is never overwritten. Source API-120 independently verifies the object before recording private metadata. IAM must restrict the integration writer to this prefix and enforce conditional writes; genuine cloud policy qualification remains a release gate.

Provider acceptance remains LABEL_PENDING until PDF production succeeds. Before S3 HTTP, an UPLOAD checkpoint pins the exact object key, SHA256 and size. A crash after acceptance can recover the matching private object through HEAD without another provider create or upload. A missing object may be regenerated only from an already accepted async job and must match the pinned bytes; otherwise uncertainty requires review. The execution checkpoint then stores the exact API-120 command UUID, occurredAt, mode, reference, object key/checksum and body before source HTTP. Source ACK response loss retries only that original body/key, without creation-context fetch, another FedEx shipment or another upload. Job SUCCEEDED/booked is recorded only after the scoped source acknowledgement; this means booking/label acceptance, never physical dispatch or delivery. Payment/stock remain commerce-owned.

No table, foreign key, public API or event shape changes. The existing kind-specific integration_job cursor holds small private checkpoint metadata, not addresses, credentials or PDF bytes. Existing generic payment jobs keep their own cursor/lease behavior. Cancellation, active tracking, manual recovery and release composition must be qualified separately before the whole CARRIER-001 task is DONE.
