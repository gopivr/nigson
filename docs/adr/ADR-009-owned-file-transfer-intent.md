# ADR-009: Owned file transfer intent and pinned scan bytes

Status: Accepted implementation decision within the authorized commerce boundary; no live activation approval.

Context: API-112 verifies quarantine bytes outside database transactions. API-132 promotes clean bytes through S3 CopyObject, which may time out after acceptance. asset_reference alone has no owner-party, pinned storage version, configured scan-command binding or copy-lease/UNKNOWN state. A browser upload UUID or a callback checksum alone cannot establish ownership or safe promotion.

Decision: Add commerce.files-owned file_transfer as a BP1 additive migration. It links only commerce asset_reference/party, records creator ownership, immutable quarantine/final keys, five-minute upload expiry, source version/ETag from verified HEAD, emitted EVT-025 event ID as scan command ID, closed callback hash/result/scanner revision and bounded copy lease/state. State UPLOADING -> QUARANTINED -> COPYING -> CLEAN or UNKNOWN; QUARANTINED -> REJECTED. UNKNOWN is reconciled by HEAD of the deterministic final object, never blindly recopied. Callback commandId must equal the scan event ID and trusted configured integration scope/client; only the pinned source version is copied. Rejected/terminal outcomes cannot be reversed by out-of-order callbacks. Public business publication remains separate.

Contracts: API-111/112/113/132 and EVT-025 shapes remain unchanged. linkedResourceId resolves only an owned product or SKU; detached browser uploads are creator-only. Browser purposes IMAGE/BROCHURE only. SHIPPING_LABEL is generated by the carrier contract and remains PRIVATE/OPERATIONS-only. The existing catalogue local asset port receives final clean references; no cross-owner entity/SQL/FK is introduced. Storage port uses real S3 SDK, explicit dummy credentials only for an allowlisted local endpoint and ECS task credentials outside local/test. Production missing storage configuration fails closed; no mock fallback.

Migration analysis: New table/constraints/indexes/grants are a separate changeset after existing BP1 schema, inherited by subsequent release wrappers. Existing applied DATA-001 files and checksums are preserved. The normative catalog/manifest/generator recognize this additive increment explicitly. Rollback refuses populated transfer evidence. Owner runtime may mutate its rows; other owners receive no grants. Native verification must exercise empty schema, upgrade from previous BP1, repeat/no drift, cross-owner denial and safe populated rollback before DONE.

Alternatives: Holding asset locks over S3 HTTP violates section17; trusting current quarantine key without a pinned version permits byte replacement; reusing configuration or unrelated job entities obscures ownership; treating copy timeout as success discards uncertainty. Retention deletion and genuine scanner/storage qualification remain separate release inputs/tasks, without invented approvals.
