# Paystack launch qualification

Paystack is the sole launch payment provider. Commerce owns its credentials and financial state; integration receives only the scoped reconciliation interface. MOCK, TEST and LIVE use the same PaystackAdapter and owned order/payment pipeline. Changing modes changes configuration, never settlement, refund, signature or stock rules. See [payment recovery](payments.md) for durable receipts, partial refunds, UNKNOWN recovery and expiry races.

Run `ENV=test make paystack-check` with the pinned Java toolchain and local Docker. This runs seven pure release-preflight checks, the real HTTP Paystack/FedEx/Twilio/email regression, then isolated PostgreSQL payment/order acceptance with Paystack mode checks. HTTP mocks use synthetic keys and actual HMAC signatures. No genuine provider is contacted. Constructor-only TEST/LIVE checks validate configuration shape and do not qualify credentials or accounts. The native financial harness checks actual once-only settlement/refunds, callback duplicates and changed bodies, out-of-order truth, lost accepted responses, exact NGN kobo, current authority, atomic audit/outbox and competing expiry/settlement.

MOCK is restricted to local/test HTTP mock targets. TEST requires the official HTTPS API and a test key; production requires LIVE and a live key. Enabled payments also require actual merchant/key association and explicit integration metadata, purpose-bound receipt keys, qualified provider proof and approved selling policies. Known dummy, fixture, synthetic, configuration-only and all-zero keys fail closed before HTTP. Arbitrary key syntax cannot establish account ownership; that association requires actual provider qualification.

For genuine read-only qualification, supply actual `ENV=stage`, `PROVIDER=paystack`, `PAYSTACK_MODE=TEST`, `PAYSTACK_BASE_URL=https://api.paystack.co`, securely resolved `PAYSTACK_SECRET_KEY`, `PAYSTACK_QUALIFICATION_REFERENCE` and positive integer `PAYSTACK_QUALIFICATION_KOBO`. Invoke `python3 scripts/platform/provider_live_check.py` using the pinned Java toolchain. The reference must identify an actual settled test payment under those credentials. The wrapper validates all selected configuration before any build or HTTP; errors report setting names only. Verification requires matching TEST domain, reference, NGN amount, successful status, positive actual provider transaction ID and parseable paid_at. It creates no charge or refund and logs no response or credential. A pending reference cannot qualify successful settlement.

This read-only check covers one actual verification response. Hosted checkout, signed account callbacks, partial/full refunds, account/integration binding, expiry/recovery and bounded live smoke still require genuine end-to-end evidence and approved release configuration. Do not infer those gates from mock or read-only checks. Store credentials in approved secret references and record safe mode/config revisions, actual command results and commit hashes. Genuine qualification remains NOT_RUN until actual credentials/account metadata are supplied. Carrier, messaging, identity, infrastructure, restore and security remain mandatory BP1 gates.

Protocol sources reviewed 11 October 2026: [transactions](https://paystack.com/docs/api/transaction/), [refunds](https://paystack.com/docs/api/refund/) and [test payments](https://paystack.com/docs/payments/test-payments/). Provider documentation informs adapter contracts; synthetic fixtures establish no merchant or service approval.
