# Commerce owner configuration

API-135 is `PUT /api/v1/commerce/staff/configuration/{key}`. It requires a current commerce ADMIN with no organization context, an encrypted BFF session, cookie CSRF, a quoted numeric If-Match and Idempotency-Key. Browser bearer tokens remain denied. Reject unknown/repeated query parameters, duplicate headers, unknown JSON fields and non-JSON bodies. Responses contain exactly key, revision, active and version, with ETag and Cache-Control:no-store.

The first registered engineering key is `catalogue.metadata`. No real units, divisions or specification definitions are seeded. Its closed value has schemaVersion1, units and divisions; the reviewed OpenAPI describes bounds and attribute types. Codes and attribute keys are unique; unit scales are integers0–3, and numeric attributes may reference only a registered unit. No credential/provider/account fields are accepted. The entire command is limited to64KiB, with a bounded NFC reason of10–500 characters. Free-text reasons and raw values are excluded from audit; durable request storage keeps their canonical hash and minimal response.

An absent key has expected version0. Creating it with If-Match:"0" returns revision/version1; a second first-write request becomes412. Each later successful command appends a new immutable row with the next key revision/version; no-op submissions with a new request key also record the operator decision. Historical active flags describe history. Consumers must use the latest revision only, and its inactive state disables use. The first row ID is the stable audit resource; each historical row has its own UUID. Retention/purge remains a release governance input; this endpoint does not delete history.

All activation requires signed MFA within15 minutes. catalogue.metadata activation requires at least one explicitly supplied unit, preserves every existing SKU unit/scale and validates existing product specifications. Staged inactive metadata still receives structural validation. Active approval records the verified ADMIN Party identifier, without fabricating an external business approval. Exposure never grants a user permission. No external provider activation key is registered; attempting one fails PLATFORM_RULE_VIOLATION rather than enabling an incomplete policy.

The owner ledger and revision/audit mutation are transactional. A key-scoped PostgreSQL advisory lock serializes competing writes; a Party share lock stabilizes current authority against concurrent role revocation, followed by another owned authorization check. Lock waits are bounded500ms and statements2s. Current authorization and activation MFA are also checked before replay; the original minimal response is replayed for a matching key/body/version. Different canonical input gives409; stale version gives412. Audit insertion failure rolls back the new revision. No domain event or provider HTTP call occurs.

Catalogue commands using this metadata must take the same `configuration:catalogue.metadata` advisory lock before reading the latest policy and changing SKU/specification meaning. This prevents concurrent policy activation from invalidating a product write. Catalogue endpoint implementation owns that dependent integration and remains IN_PROGRESS.
