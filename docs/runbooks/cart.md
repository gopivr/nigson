# Owned carts

API-032 creates or returns the one ACTIVE context for the current customer, optional currently entitled organization and enabled NG/NGN2 market. The nil organization sentinel is an index detail; nil business UUIDs and explicit null optional inputs are rejected. Returning an existing context preserves its version and activity.

API-033 reads current owned state in a bounded repeatable-read transaction. All four routes return `Cache-Control: no-store`; successful responses carry the aggregate ETag. Cart state and private lines never use a shared cache. Guests and browser bearer tokens remain denied by the JDBC BFF security boundary.

API-034 requires CSRF, an idempotency key and the quoted current ETag. A positive quantity must satisfy current SKU scale, pack, eligibility, effective price and applicable wholesale quantity/pack rules. The line, aggregate version/activity, audit and acknowledgment commit together. A cart has at most100 distinct lines. Whole-order minimums are enforced at checkout so a customer can build a wholesale cart incrementally. Cart edits do not reserve stock or call providers. An edit invalidates older carrier/checkout bindings through its cart version.

API-035 removes an existing line from an owned ACTIVE cart with the same mutation headers. Use DELETE for zero quantity. An inactive SKU can still be removed. Its204 response has no body and carries the resulting ETag. Missing lines are404; stale revisions412; non-ACTIVE states409. A matching durable key replays the original response and ETag. Fetch API-033 for current state after replay; use a fresh key for a new intended mutation. Conflicting input with the same key409. Bounded lock contention returns409 so the same request can be retried after the active command completes.

Current Party identity/status and current organization membership/explicit configured buying entitlement are checked before cached acknowledgments. The existing pricing configuration supplies the exact entitlement mapping; its empty default denies organization shopping. Production organization activation needs the reviewed mapping and owning entitlement workflow, not an arbitrary active entitlement.

`CartCheckout` is a commerce-local transaction port for the owning order/payment workflows. T1 locks the cart, checks current aggregate version and unexpired stored quote/hash, validates the actual pending order context, and marks CHECKOUT_PENDING. Its changes roll back with the caller transaction. Settlement and expiry lock order first and then cart. Conversion requires the current paid financial status plus a successful verified attempt and matching append-only payment transaction. Duplicate terminal transitions return existing state without another audit/version increment. Verified late settlement can convert an EXPIRED cart; cart conversion never changes inventory or order fulfillment state.

Pending expiry requires a cancelled unpaid/failed order, no uncertain/unverified attempts, no payment transactions and no RESERVED/ALLOCATED stock. A timeout, expired URL or UNKNOWN attempt cannot establish failure. The payment owner must reconcile provider truth and the inventory owner must release stock using their transaction rules. This port changes only cart state and never rewrites financial evidence. There is no invented automatic ACTIVE-cart retention or deletion policy.

Recovery eligibility is an internal foundation predicate: current owned ACTIVE cart, nonempty lines, at least24h inactivity and no linked order or later paid context order. It locks the cart and makes no consent, contact, URL, send or campaign decision. COM-CART-002 owns API-159/candidates/consent recheck and notification orchestration. Eligibility alone authorizes no send and does not expire a cart.
