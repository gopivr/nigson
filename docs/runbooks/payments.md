# Payment verification and refund recovery

Commerce owns payment credentials, settlement, refunds and encrypted callback receipts. Integration calls API-118 with private ingress and the exact `nigson-integration` workload JWT/scope `payment.reconcile`; it receives only processed count, next cursor and mismatches. Browser payment reads require the current order owner. Refund request, approval and detail require current persisted FINANCE authority and MFA within15 minutes; cookie mutations also require CSRF, Idempotency-Key and If-Match. Request If-Match refers to the order; approval If-Match refers to the refund. Refresh on412 and use a new key for a changed intended command.

Payments are disabled by default. Enable `NIGSON_PAYMENT_ENABLED` only with the accepted order/provider configuration, matching PAYSTACK_MODE/order mode, actual merchant/key association and explicit `NIGSON_PAYSTACK_INTEGRATION_ID`. No account identifier is supplied by application defaults. Production requires LIVE and qualified activation inputs. `NIGSON_REFUND_TWO_PERSON` defaults true; disabling it outside local/test requires the actual approved `NIGSON_REFUND_APPROVAL_POLICY_REFERENCE`. An approval queues a durable intent; it does not assert successful refund.

Receipt encryption has a separate key purpose. Configure `NIGSON_PAYMENT_RECEIPT_KEY_REVISION`, `NIGSON_PAYMENT_RECEIPT_KMS_KEY` and `NIGSON_PAYMENT_RECEIPT_WRAPPED_KEY`. KMS encryption context is purpose `nigson-commerce-payment-receipts` plus revision; session-wrapped keys cannot substitute. `NIGSON_PAYMENT_RECEIPT_PREVIOUS_WRAPPED_KEYS` is a JSON object with at most two previous revision/wrapped-key pairs. Keep the keys needed to read retained receipts until an actual retention/rotation approval permits removal. `NIGSON_PAYMENT_RECEIPT_LOCAL_KEY` accepts a32-byte Base64 key only in local/test, without KMS/wrapped/previous-key configuration. Never put keys or raw provider bodies into logs, events or support tickets.

API-042 authenticates HMAC-SHA512 against exact raw bytes before parsing; the body limit is256KiB. The synchronous200 means the encrypted receipt and audit committed. Stable provider object/event identity deduplicates matching callbacks; changed bodies are separately quarantined and the first payload remains intact. Receipt processing decrypts with receipt/account/mode/body-hash context, performs independent provider HTTP outside transactions and applies only matching stored financial truth. Out-of-order refund callbacks cannot regress successful money. Check RECEIVED/RETRY/APPLIED/REJECTED and the safe rejection code; receipt itself never authorizes revenue or stock allocation.

The owned worker polls durable approved refunds, receipts, due payment attempts and reservation expiry. `NIGSON_PAYMENT_WORKER_ENABLED` defaults true when payments are explicitly enabled; `NIGSON_PAYMENT_WORKER_BATCH` defaults25 and is bounded1..100. Fixed delay defaults30000ms through `NIGSON_PAYMENT_WORKER_DELAY_MS`. Provider calls have their own deadlines; each poll stops starting new work after its20-second budget. A failed item remains durable and logs only PAYMENT_WORK_RETRY_REQUIRED. Multiple replicas may verify the same item; order/attempt/refund locks and immutable financial business keys prevent duplicate effects. Refund submission claims APPROVED->SUBMITTING before HTTP, with a30-second recovery lease; expired claims become UNKNOWN and are never blindly resubmitted.

After lost refund response, inspect the actual provider list by the independently verified transaction ID, stable merchant_note, mode/account integration, currency and exact kobo amount. Lookup is bounded to ten100-record pages and a deadline; incomplete/ambiguous lookup stays UNKNOWN. Only a subsequent matching provider GET result can confirm success or failure. Absence from a bounded list is not proof of failure. Do not manually change UNKNOWN to APPROVED or issue another provider refund. A processed refund commits refund state, order refunded total, history, audit and EVT-012 atomically. Failed refunds release only the monetary reservation. Financial refunds never restore inventory; physical returns/unshipped reversals use the fulfillment stock-return workflow.

Reservation expiry first verifies outside DB transactions, then locks order/attempt. `NIGSON_PAYMENT_UNCERTAIN_GRACE_SECONDS` defaults3600 and is bounded60..3600. Within grace, uncertain stock remains reserved. After grace, cancellation releases stock and expires the cart while keeping the payment attempt UNKNOWN, order payment status PENDING and late monitoring. This system transition is separate from API-040, which still refuses customer cancellation on uncertainty. Late verified success either re-reserves/allocates available stock or retains PAID financial truth with PAYMENT_HOLD/STOCK_UNAVAILABLE. A repeated verification cannot silently resolve a hold. Finance/customer-approved resolution remains necessary before fulfillment.

API-118 requires a stable jobId, limit1..100, Idempotency-Key and optional opaque cursor. It commits the canonical intent and immutable batch plan before HTTP, then stores the final response. Identical replay returns that response; changed input conflicts before provider calls. Use nextCursor with the same jobId and a new command key for the next page. processed counts inspected work items; mismatches counts rejected callback evidence. UNKNOWN is monitored rather than counted as a fabricated provider mismatch or success. No provider secret or raw body leaves Commerce.

Observe closed `nigson.payment.outcomes`, `nigson.payment.receipts`, `nigson.refund.commands` and `nigson.refund.outcomes` labels alongside audit/outbox health and private order/refund state. Never add account, reference, party or transaction identifiers as metric labels. Audit/outbox failures roll back local financial mutations; retained provider truth is recovered by independent reconciliation. After restore, run reconciliation before assuming the backup matches provider settlements or refunds.
