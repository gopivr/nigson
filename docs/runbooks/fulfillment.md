# Delivery rules, shipments and physical returns

API-171 creates and API-047 updates explicit delivery fees for approved NG/NGN2 coverage. Current OPERATIONS, cookie CSRF and durable request keys are required; updates require quoted If-Match. Rules select the most specified dimensions (region/postal), then longest postal prefix, then highest priority. Active tied overlapping matches are rejected under context serialization. Money uses NGN2 and an explicit freeAbove threshold applies at equality. Queries lock/read current owned metadata and bounded rules; no implicit zero fee or current price cache exists. The local DeliveryRules port does not replace a live FedEx quote without the carrier owner's explicit composition.

API-048 locks the actual paid unheld order and checks successful verified Paystack settlement, matching frozen carrier/provider mode, allocated stock, refund/cancellation limits and all existing shipment claims. It freezes typed minimal address, approved service, server-packed parcels and a stable booking reference. Explicit FEDEX starts CREATED and atomically emits EVT-009 and EVT-027; the integration worker calls the carrier after committing its own durable job. A browser providerReference or tracking URL cannot establish FedEx booking.

Shipping is disabled by default (`NIGSON_FULFILLMENT_ENABLED=false`). Enabling requires explicit mode, reviewed approval reference and future approval expiry. MOCK is restricted to local/test; production requires LIVE and cannot fall back. Frozen order carrier_snapshot must contain provider FEDEX, currency NGN, mode and serviceCode; order/payment composition must preserve these from the qualified carrier quote. Shipment package_snapshot is schemaVersion1 with mode, serviceCode, minimal CarrierAddress, bounded CarrierPackage list, packageHash, bookingReference and approvalReference. These are owned PostgreSQL snapshots; the BFF ShipmentDTO exposes none of the booking/label/private address metadata.

API-048's contractual MANUAL default is preserved as a contingency. It fails without an explicit current `NIGSON_FULFILLMENT_MANUAL_CONTINGENCY` reference. An operator-supplied providerReference records MANUAL BOOKED/READY evidence under this configuration; absence leaves CREATED. It does not assert a FedEx success. Normal launch logistics require FedEx/private integration. Actual API-119/120, label verification, carrier reconciliation and provider qualification are required CARRIER-001 BP1 work despite historical BP4 labels.

API-049 requires current OPERATIONS, CSRF/key/If-Match and READY with provider reference and durable BOOKED evidence. FEDEX additionally requires a CLEAN PRIVATE SHIPPING_LABEL owned by this shipment. Label creation alone never dispatches stock. The transaction calls StockLedger once with the shipment business identity, decreases on_hand/allocated together, records shipment/order history and outbox, and leaves financial truth intact. UNKNOWN/CREATED, held orders or missing proof cannot dispatch. Duplicate/stale commands cannot double debit stock.

API-050 accepts only SHIPPED and actual deliveredAt between dispatch and current time. Partial deliveries keep the order incomplete; all eligible quantities must be delivered before aggregate DELIVERED. Payment status and totals remain financial-owner truth. Customer/staff tracking callbacks and out-of-order provider projection are separate owning tasks; these commands do not infer carrier HTTP success.

API-174 requires current OPERATIONS and a durable key. PHYSICAL_RETURN needs an explicit verified receipt and cumulative dispatched-quantity guard. The canonical SHA256 identity binds order/kind/receipt, so a different HTTP key for the same receipt cannot add stock again; changed contents conflict. UNSHIPPED_CANCEL requires an authorized cancelled/refunding/refunded order and releases allocation without increasing on_hand. If its reference is omitted, the server derives a stable command reference; no physical evidence is invented. Monetary refund and physical stock receipt are separate actions. A return changes no payment status/amount and does not require a fabricated refund success.

All mutations audit and commit acknowledgments atomically. Locks/statement waits are bounded; conflicts409 can retry the same intended key, stale412 needs a fresh state/version, and invalid state/rules409/422 need correction. Matching replay returns the original acknowledgment; current Party/role checks precede it. No provider HTTP occurs in these order/stock transactions. Tracking URLs must be HTTPS, without credentials/fragment/nonstandard port, and use an exact configured host in `NIGSON_FULFILLMENT_TRACKING_HOSTS`.
