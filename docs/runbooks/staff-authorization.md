# Staff authorization operations (COM-AUTHO-001)

API-011/012 run inside commerce and require `NIGSON_SECURITY_ENABLED=true` and the SEC-001 configuration. The default foundation application still denies domain routes. There is no identity-provider role synchronization: authority comes from active commerce parties and their unrevoked assignments. ADMIN does not imply FINANCE. A browser uses the server-side BFF cookie; browser bearer and private workload credentials cannot substitute.

Search mapped staff through `GET /api/v1/staff/users`, including staff whose assignments were revoked. Retail-only identities are excluded. Queries are bounded to 100 results, literal case-insensitive name/email search, and an explicit sort allowlist. The default sort is createdAt descending with UUID tie-break. All responses use no-store. StaffDTO contains only id, displayName, email, roles and the Party aggregate version.

To replace roles, send `PUT /api/v1/staff/users/{id}/roles` with JSON roles and a reason of 10–500 characters, quoted If-Match, an Idempotency-Key and the session's X-CSRF-TOKEN. Staff MFA must be signed identity evidence no older than 15 minutes. CUSTOMER and service roles cannot be assigned. An empty list removes staff privileges. The target must already be mapped staff and ACTIVE. Initial controlled provisioning is separate from these endpoints.

The command rechecks the actor's active party/identity/ADMIN assignment under owner locks. A commerce advisory transaction lock, key `711938201104`, serializes role changes, followed by actor/target Party locks in UUID order. Count only ADMIN assignments belonging to ACTIVE parties when protecting the last administrator. A future party suspension/anonymization or alternate staff administration workflow must use the same lock and last-admin invariant before changing authority; raw runtime SQL is not an administration interface. No provider HTTP occurs inside these transactions. Lock contention is bounded to one second and returns a safe conflict; refresh/retry the same business request.

The role set, individual assignment audit entries, Party version and target session deletion commit together. Audit failure rolls back all effects. Audit keeps the typed OPERATOR_REQUEST reason and each changed role; arbitrary free text is redacted by the existing audit policy. A no-op preserves the version and sessions. Matching idempotency replay returns the original DTO and ETag after current actor authorization; a changed input with the same key returns409. A stale new command returns412. If the response was lost, retry the original key/input; a role change affecting the actor revokes that actor's sessions, so reauthenticate with current privileges before retrying. Do not create a new key merely because the first response was lost.

First administrator provisioning requires an approved Keycloak issuer/subject mapped to a commerce Party, an approved operator and an audited commerce-local transaction. Never infer the subject from email or seed a production administrator from test fixtures. Before activation, the operations owner supplies those explicit identities and records the provisioning evidence. Existing local identity fixtures are not rewritten by this task. Party provisioning and BFF public login/session controllers remain COM-PARTY-001 and COM-SESSI-001.

Observe API-011/012 through the existing bounded HTTP route metrics, database timings, audit persisted and idempotency replay/conflict counters. Logs contain safe error codes and correlation/trace identifiers; never log the request reason, email, identity subjects or session material. Inspect owned append-only audit records for individual changes and correlation; investigate a500 before retrying, while retaining evidence. A422 indicates last-active-admin protection and requires an authorized additional administrator before removal. A403 requires reauthentication/current commerce authority, never a role copied from a Keycloak claim.
