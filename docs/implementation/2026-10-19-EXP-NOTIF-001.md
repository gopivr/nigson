## Summary

Implemented API-137 `POST /internal/v1/notification-deliveries` as an exact `nigson-integration` workload operation requiring `notification.write`, with a closed request DTO, bounded provider-reference validation, Experience resource ownership checks, no-store response, safe errors, owner-local metrics, and durable request replay through the existing Experience idempotency ledger. Each job’s outcomes are recorded append-only in `experience.audit_record`, using a job-scoped advisory lock to deduplicate concurrent job/state acknowledgments and bind the job to one Experience resource. Repeated current outcomes acknowledge without a second audit row. UNKNOWN can reconcile only to SENT or FAILED; terminal/stale/out-of-order outcomes are rejected. Provider references are validated but not retained. API-137 never dispatches or retries provider work.

The generated Experience OpenAPI now describes API-137 and its exact workload scope. No migration or event was needed: the existing owner audit and idempotency records provide the required persistence and there is no side effect needing an outbox.

The accepted notification ownership boundary remains in effect. Integration owns escaped template rendering, durable provider attempt rows and provider UNKNOWN reconciliation; its existing Twilio sender/receipt paths were regression-tested. Integration must use the existing Experience API-127 eligibility call immediately before a provider send. API-137 has no channel, purpose, destination, or resource version in its public DTO, so adding an independent consent query or `If-Match` would change that contract. The outcome endpoint does not represent send consent or authorize sending. Fresh API-127 consent/suppression behavior remains tested through the existing sender path. Real sender/template/account approvals and live dispatch qualification remain NOT_RUN.
