## Result and repository ownership

User requested a build/deployment workflow in the separate UI repository. Added UI workflow build and deploy UI to AWS staging. PRs build/test only. Pushes to main and manual default-branch runs may deploy stage after a successful build. A credential-free Node24.15.0 job builds shell and every configured remote, seals file hashes/commit and uploads only that static artifact. A fresh protected-stage deployment job obtains the exact successful build artifact ID, checks current UI default-branch head, reads backend tooling using a Contents:read token, and uses the existing AWS credentials/account/region. Retry-only deployment jobs reuse the original artifact ID and choose a new immutable release prefix. Deployment jobs serialize without cancelling running releases.

The backend remains the only Terraform/state owner. A new sensitive versioned deployment_configuration output records every applied root input. Frontend deployment loads this complete snapshot, retains runtime activation flags, images and environment settings, and changes only frontend_release_id. It discovers the existing bucket/distribution from state and checks account/bucket ownership/exact staging alias. No manually copied resource IDs or second frontend Terraform state. Missing/incomplete snapshots fail with an infrastructure-preparation instruction. The foundation workflow preserves the current frontend release from snapshot or legacy output rather than restoring initial.

Release activation intentionally targets the existing CloudFront distribution, then validates the saved plan: only an in-place static origin_path change is permitted. Extra resource changes, replacement, changed backend origin/TLS/WAF and other distribution settings fail before upload. Computed read-only metadata is excluded; the AWS6.15 unset/zero response timeout representation is normalized only because both omit that API field. Positive configured timeout changes are rejected. Upload uses the existing validated immutable-prefix publisher; the exact saved plan is applied afterwards with state locking/stale-plan checks. The workflow waits for CloudFront deployment, invalidates caches, waits, and probes exact shell/manifest/all federation-entry bytes over HTTPS without redirects. Existing release objects remain for recovery. It never activates backend services or invokes business providers.
