## Summary

Implemented Experience-owned APIs 087, 089, 090, 091 and 129 over the existing `experience.lead` and `experience.lead_activity` tables. Public CONTACT/COMPLAINT intake validates closed, bounded input, checks an explicit anti-abuse/rate-limit port and commits the lead, initial activity, audit, idempotent response and PII-redacted EVT-016 atomically. A failed event publication leaves the intake durable and the outbox retryable. No mail or external provider call runs in the database transaction.

Staff list/detail/update require the exact Commerce workload route plus a current signed SALES or ADMIN actor. SALES sees assigned and unassigned triage records; assigned records are concealed from other staff. The list is bounded and deterministically ordered. Updates require `If-Match` and `Idempotency-Key`, self-claim assignment validation, allowed state transitions, immutable activity history, audit and version advancement. Integration API-129 requires its exact workload scope and returns only configured recipient group, lead type, subject and HTTPS admin link; it does not expose contact or message content.

The existing API-088 quote intake/association remains intact. Existing inbound WhatsApp lead creation now uses the configured recipient group instead of a hard-coded `SALES` value. No schema migration was needed. Missing recipient group, HTTPS admin base URL, anti-abuse verifier or rate limiter fails closed. The provided HMAC verifier and local limiter are test/local-only; no production sender, recipient, retention, privacy or live-provider configuration was invented.
